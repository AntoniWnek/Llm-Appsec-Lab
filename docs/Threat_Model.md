# Threat Model — Enterprise HR Copilot (OWASP LLM Top 10 2025)

## 1. System Overview & Assets

The Enterprise HR Copilot assists recruitment personnel by querying an internal SQLite database (`data/hr_lab.db`) and summarizing candidate resumes uploaded in `.pdf` or `.txt` formats.

### Crown Jewel Assets
1. **Confidential Executive Compensation (`board_salaries` table):** Contains executive names (`Marek Zielinski`, `Anna Wisniewska`, `Piotr Kaminski`), base salaries, bonuses, and the Canary Honeytoken (`CONF-HR-9921-X`).
2. **System Instructions & Internal Routing Logic:** Internal prompt directives and database schema definitions.
3. **Recruiter Browser Session:** The web client rendering Markdown responses generated by the assistant.
4. **Database Integrity:** The integrity of records inside `candidates` and `board_salaries`.

---

## 2. Threat Actors & Trust Boundaries

The threat model distinguishes between two distinct adversarial profiles operating across different trust boundaries:

### Threat Actor 1: Insider Threat (Unprivileged HR Employee)
- **Access Level:** Authenticated access to the HR Copilot chat interface (`ATK-01` through `ATK-05`).
- **Authorization Boundary:** Authorized to query public candidate applications (`candidates` table), but **unauthorized** to view executive compensation (`board_salaries` table).
- **Objective:** Privilege escalation via Direct Prompt Injection, encoding/obfuscation bypasses, or LLM-driven SQL Injection to extract `board_salaries` records.

### Threat Actor 2: External Unauthenticated Applicant
- **Access Level:** Zero access to the internal network or chat interface (`ATK-06`).
- **Attack Vector:** Submits a crafted `.pdf` resume (`data/poisoned_cv.pdf`) via the recruitment pipeline.
- **Objective:** Indirect Prompt Injection (XPIA). When an innocent recruiter uploads the PDF and asks for a summary, hidden instructions inside the PDF hijack the LLM control flow, query `board_salaries`, and exfiltrate the result to an external listener (`http://127.0.0.1:8888/leak`) via an invisible 1x1 Markdown image request rendered by the recruiter's browser.

## 3. Vulnerability Mechanics (Vulnerable Mode Analysis)

### 3.1. TOCTOU Input Normalization & Base64 Decoding (`ATK-03`, `ATK-04`)
In `Vulnerable` mode, the application checks user chat input against a naive keyword blacklist (`board_salaries`, `ceo salary`, etc.) *before* normalizing Unicode characters or decoding embedded Base64 blobs:
- Submitting `b\u200board_s\u200balaries` evades the exact string check. Subsequent stripping of `U+200B` reconstructs the forbidden table name for the downstream LLM.
- Submitting a Base64-encoded SQL statement bypasses the keyword filter and is decoded prior to model invocation.

### 3.2. Naive SQL Substring Validation (`ATK-05`)
The vulnerable `run_raw_sql` function checks whether `"from candidates"` appears in the lowercase SQL query string. An attacker bypasses this check by instructing the LLM to execute a compound query:
```sql
SELECT full_name, role, application_status FROM candidates
UNION
SELECT executive_name, title, confidential_marker FROM board_salaries;
```
### 3.3. PDF Parser Differential / Off-Canvas Injection (ATK-06)
In `src/generate_cv_pdfs.py`, the adversarial instruction block is positioned using the raw PDF text matrix operator `-5000 -5000 Td` with `1pt` white font (`1 1 1 rg`). Because standard page dimensions are defined as `MediaBox [0 0 612 792]`, PDF viewers clip and hide any text rendered outside those coordinates. However, `pypdf` extracts all text operators from the content stream regardless of spatial coordinates, delivering the hidden payload directly into the LLM prompt.

## 4. Defense-in-Depth Mitigations (Hardened Mode)
| Layer | Component | Technical Implementation | Mitigated Risks |
| --- | --- | --- | --- |
| 1. Input Normalization & Guardrails | `src/guardrails.py` (`inspect_user_input`) | Strips zero-width Unicode (`U+200B`–`U+200F`, `U+FEFF`) before evaluating regex heuristics and character length limits. | `LLM01:2025`, `LLM07:2025` |
| 2. Structural Document Sandbox | `src/guardrails.py` (`sandbox_cv_document`) | Truncates fake document boundary markers (`--- END OF CANDIDATE CV DOCUMENT ---`), neutralizes embedded image tags, and wraps resume text in `<untrusted_cv_data>` tags. | `LLM01:2025` (Indirect XPIA) |
| 3. Schema Validation & Parameterized SQL | `src/tools.py` (`search_candidates_safe`) | Replaces raw SQL generation with a fixed parameterized `SELECT` statement (`?` placeholders) backed by strict Pydantic validation (`CandidateSearchParams`). | `LLM05:2025`, `LLM06:2025` |
| 4. Engine-Level SQLite Authorizer | `src/tools.py` (`_hr_sqlite_authorizer`) | Enforces `sqlite3.SQLITE_DENY` at the SQLite C-driver level whenever any query references `board_salaries` or attempts non-read operations (`DELETE`, `UPDATE`, `DROP`). | `LLM06:2025` (Excessive Agency) |
| 5. Output DLP & Markdown Sanitizer | `src/guardrails.py` (`inspect_and_sanitize_output`) | Blocks any output containing the Canary Honeytoken (`CONF-HR-9921-X`) or executive names, and rewrites `![alt](http://...)` tags into inert text labels. | `LLM02:2025`, `LLM05:2025` |

---

## 5. Engineering Trade-offs & Residual Risk
1. **Heuristic Input Filters vs. Hard Backend Controls:** Regex-based input guardrails (Layer 1) provide fast, zero-cost rejection of known attack signatures (< 0.5 ms), but cannot catch every novel semantic paraphrase. Therefore, the architecture does not rely on Layer 1 for data confidentiality; even if Layer 1 were completely disabled, Layers 3 and 4 (Pydantic + sqlite3.set_authorizer) mathematically prevent unauthorized queries against board_salaries.

2. **Small Local Model Tool-Calling Reliability:** Smaller local models (e.g., 1.5B–3B parameter models running on CPU via Ollama) occasionally emit tool invocations as raw JSON strings inside message content rather than native tool_calls structures. The orchestrator in src/agent.py includes a deterministic fallback parser and restricts execution strictly to the active mode's allowlisted function.
